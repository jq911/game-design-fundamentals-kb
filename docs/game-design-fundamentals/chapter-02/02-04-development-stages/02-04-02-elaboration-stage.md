# 2.4.2 细化阶段

> 来源：私人资料库 OCR 整理，摘自《游戏设计基础（原书第 3 版）》第 2 章。PDF 为扫描版，文字已做轻度校正，仍建议以后逐段人工复核。  
> 关键词：概念设计、细化阶段、调整阶段、原型、迭代

## 原书内容整理

一旦你在概念阶段对于游戏做出了基本决定，那么接下来就可以进入游戏设计的细化43阶段了。在这个环节，设计工作将更为具体，从理论升华到实际。在细化阶段，通常你开始与一个小型开发团队合作构建游戏的原型。如果你计划采用全新的想法或技术，你的团队还应建立一个测试平台或技术演示来试用它们。从现在起，你可以采取你的设计想法，让开发团队在原型中实现它们，看看它们在实际中如何工作，并根据你所掌握的知识再去改进它们。在本阶段中，你的游戏项目应该能得到某个资助机构的帮助（希望如此），从而进入全面生产。犹豫不决的风险从概念设计到细化阶段，中间的过渡是一个非常关键的时刻。在这个时间点上，最重要的决定便是“落地生根”，换言之，就是确立基本框架。一些设计师不愿意做这种事情，不想把话说得太死，他们会说自己是在“保留意见”。这是因为他们害怕可能会做出错误的决定，或者忽略了某些东西。这种不负责任的后果通常是灾难性的。如果最关键的细节在游戏进入全面生产阶段时仍可以随意修改，那么开发团队永远不会确切地知道自己的工作目的。设计师不断地需要对代码和内容进行大量的更改，生产将会变得缓慢和低效。这是缺之远见和信心的典型迹象。陷入这个泥潭的游戏项目基本会被取消，绝难有完工之日。当你开始设计细化阶段时，如果你有一个由若千成员组成的团队，那么就有可能并行地开始设计任务。一旦所有人都在游戏的基本原理上达成了共识，那么每个设计师便可以在一个特定的责任领域内开始工作了。这个重复改进的过程不是在游戏开发的后期引入重大变化的借口，也不要在没有宣布完成的情况下无止境地调整它。你的目标是构建和发布已完成的产品

#### 1. 原型设计

原型是一个简化的，但可进行测试的游戏版本。设计师会在正式投入时间和物力之前使用原型来测试游戏的功能。有时设计师还会让目标人群参与游戏原型的测试，以此来判断该游戏是否让玩家感到满意。在JorisDormans和ErnestAdams的书《游戏机制：高级游戏设计》中，他们定义了游戏开发人员所使用的3种常见原型：软件原型、纸张原型和物理原型（Adams和Dormans，2012，第15～21页）。这里会简单介绍一下。更多详细内容请参阅《游戏机制：高级游戏设计》一书。如果要构建一个软件原型，那么所创建的软件内容不需要完整包含整个游戏的方方面面，只需测试其中的某一部分即可。像GameMaker这样的工具比从头开始做起来要容易得多。你还可以在开发环境中构建软件，例如Unity，AdobeFlash或HTML5，它们会为你

#### 设计点拨

供许多功能。当然，想要做好这一点，你首先得有一个程序员朋友，要不自己就是一名程序员。编写软件允许你创建一个高仿真的原型，它与真实游戏非常接近（虽然软件原型也可能是低仿真）。制作软件原型比其他类型需要更长的时间，但它产生的结果可以很容易地转化为真实的东西。但是，不要假设在最终的游戏中你会使用为原型创建的软件。制作原型的要点是能够快速完成，而不必担心代码或图形的质量。

#### 设计点拨

在创建原型时可以抛弃所有的音效、艺术和代码。这样一来你的艺术师、音效师和程序员就可以快速地进行工作，而不必担心以后的调试内容中的漏洞。试图在预生产期间就构建好生产质量管理体系，以防因质量管控问题延误时间。此外，你不必在同一个软件原型中实现游戏的所有方面。例如，你可以在几乎没有图形的原型中实现游戏的内部经济，并在不包含工作机制的不同原型中尝试图形引擎和用户界面。要想既便宜又迅速地制作和试玩一个游戏，你可以考虑制作一个纸质原型，一个桌面版本的游戏——棋盘游戏、纸牌游戏或其他非计算机操作的游戏。你可以和你的设计团队一起玩游戏，也可以在代表目标受众的朋友身上尝试。纸质原型不适用于需要大量数字处理的或者基于物理模型的游戏，但它作为一种测试游戏功能的方法在设计师圈子中却非常流行，在团队竞技、解谜等这些需要玩家互动的多人游戏中尤为盛行。即使游戏的一部分是基于物理模型的，你仍然可以制作一个纸质原型来测试其他部分。作为游戏设计师，你应该有一些般子、计数器或令牌（如扑克牌的筹码）、方格纸、空百卡和笔记本等物品。使用这些工具，你可以快速设计出电子游戏的纸上版本，并与朋友一起尝试。纸质原型最大的优势是它能够快速更改游戏的规则，并进行二次尝试。在物理原型中，你在现实生活中扮演玩家的角色。这可能意味着在你的游戏里构建的游戏环境中尝试战斗移动，或者玩一个涉及物理知识的游戏，例如投掷物体。显然，你不可能真的像马里奥那样跳跃，但可以使用身体和物理定律来试验游戏中可能的玩家动作，并找出实现电子游戏可能需要什么样的动画。物理原型也是进行运动捕获的自然前提，它很好地补充了纸质原型。如果你正在制作一个有策略和战术元素的游戏，那么你可以在纸质原型上测试策略部分，而在物理原型中试验战术部分。

#### 2. 定义主游戏可玩性模式

确定了游戏概念之后的第一个任务，便是定义游戏的主要游戏可玩性模式，也正是玩家将投入天量时间进行游戏的模式。大多数游戏都只有一个游戏可玩性模式，即主游戏可玩性模式。例如，在赛车游戏中，主要的游戏可玩性模式便是驾驶赛车，在商店里调整汽车是一种次要模式。而在战争游戏中，主要的游戏可玩性模式通常是各种战术和战斗。战争游戏通常也有策略模式，其中玩家计划战斗或在地图上选择征服的区域，但是他在这上面花费的时间通常会少于用于战斗的时间。在本阶段，没有必要定义出游戏的每个细节。现在要做的主要事情是找出构成游戏可玩性模式的部分：比如站在玩家的角度来观看游戏世界，影响游戏世界的交互模型，游戏世界在当前模式下带来的挑战，以及可以采取哪些行动来克服这些挑战。把这些感想都写在纸上，然后你可以详细了解这是怎么来的。

#### 3. 设计主要人物

如果你的游戏中有一个主要角色（无论它的交互模型是否基于化身），那么你必须在早期设计阶段完成这个角色。你希望玩家喜欢并关注这个角色，关心她会遇到什么。如果你为主游戏可玩性模式选择的角度是第一人称之外的任何角度，那么玩家将花费大量的时间观察这个角色，所以重要的就是她确实有趣，值得观看。你必须考虑外貌以及行为：她能够采取什么行动、她的脸和身体语言可以表达的情感、她使用的语言和词汇等。在第10章中将深入讨论这些问题。

#### 4. 定义游戏世界

游戏世界是游戏发生的地方，定义它可以说是一个巨大的任务。如果游戏世界是基于现实世界的（例如在飞行模拟器游戏中），那么你可以使用真实地点的照片和地图来创建它的外观。但如果它是一个幻想或科幻的世界，那么你必须依靠自己的想象力来创建。建立外观和感觉只是该任务的一部分。游戏世界中有许多维度：物理、时间、环境、情感和伦理等。所有这些品质的存在，都将服务和支撑起你的游戏可玩性。在第8章中将讨论这些问题。

#### 5. 设计核心机制

一旦有了想要在主游戏可玩性模式中包含各种挑战和行动的想法，你可以开始考虑核心机制如何创造这些挑战并付诸实际的行动。例如，如果你计划创建玩家积累金钱的挑战，那么你必须定义钱从哪里来，玩家必须做什么才能得到金钱；如果你创建的是让玩家进行一项运动的挑战，那么你必须考虑所有的运动特征（速度、力量、加速度、准确度等），以及这项运动所需要的其他元素；如果你创建的挑战涉及符号而不是数字关系，就像在益智游戏中，你必须考虑这些符号是什么，以及它们是如何操作的。在第14章中解释了如何创建游戏的核心机制。

#### 6. 创建额外模式

当决定游戏概念时，你可能会意识到你需要多种游戏可玩性模式，例如，你想在战争游戏中包括单独的策略和战术模式，在商业模拟中加入管理收入和支出。或者，你可能会发现，当定义主要的游戏可玩性模式和核心机制时，你需要额外的模式。现在，你正处于细化设计阶段，其中包括了设计额外模式：它们的角度、互动模式和游戏可玩性等。同时你还必须记录下所设计的游戏从一种模式转移到另一种模式的原因——游戏的结构，正如本章前文所述。不要创建非必需的额外模式。每个额外的模式都需要很多的设计工作、艺术工作、编程和测试。同时它也会让你的游戏更加复杂化。每种模式都应该以娱乐和服务玩家为主要目的，这才是游戏真正需要的。

#### 7. 设计关卡

关卡设计是游戏直接向玩家提供体验的过程，使用游戏设计提供的组件：角色、挑战、动作、游戏世界、核心机制和故事情节（如果有的话）。不必等到这些组件都设计完成后才开始进行关卡设计，但必须完成一定程度供关卡设计师参考。在细化阶段的早期，关卡设计师创造一个典型的关卡。这个关卡不应该是玩家遇到的第一个关卡，因为游戏中的第一关通常是非常简单的，这是由于玩家仍然在学习这个游戏——所以它通常作为教程关卡。因此，关卡设计师设计的代表关卡应该是游戏中更远的一关，其中已经包含了大多数的游戏可玩性。创建一个可工作的游戏关卡是游戏开发中一个重要的里程碑，因为这意味着测试者可以开始进行游戏测试了。有关关卡设计过程的概述，请参见本书的第16章。

#### 8. 编写故事情节

一些小型的电子游戏很少去描述一个故事，但大型游戏都通常会包括某种故事情节。故事有助于保持玩家的兴趣和参与度。好的故事会给玩家一个进入下一关的理由，好奇接下来会发生什么。故事可以用不同的方式与游戏可玩性集成。你的故事可能发生在玩家所玩的关卡之内，或者它只是关卡之间的过渡机制——用作完成关卡的奖励。这个故事可能是嵌入式的，带有预先写好的叙述块，或是自发式的，起因于核心机制。它可能是线性的，独立于玩家的动作，也可能会根据玩家的选择进人不同的分支。在第11章中将详细讨论所有这些问题。在细化阶段定义的故事情节，通常会与关卡设计紧密相关。

#### 9. 构建、测试和迭代

伟大的游戏设计师MarkCerny（《小龙斯派罗》《杰克与达斯特》的作者）断言，在开发的预生产过程中，设计师应该构建、测试，然后丢弃不少于4种不同的游戏原型。这可能是极端的，但基本原则是正确的。电子游戏在真正构建之前必须先进行原型开发，并且每一步都必须测试。每个新想法都要构建和试验，首先是粗制滥造的方式，然后才进人正式的产品模式。Cerny还认为，你为原型制作创建的材料都不应该进入最终产品，或者至少不应该指望它。对这个结果有一个坚定的规则，这样，你可以程序员和艺术家快速工作，建立测试平台，以及编写他们以后不会再调试的代码。如果他们试图在开发的预生产阶段构建可维护的代码或最终质量的艺术品，测试过程需要比预期长得多。一旦开发从预生产转向正式生产，团队就开始着手准备为客户提供材料，并且必须特别小心地构建。然而，你仍然有一些自己无法设计的东西，把这项工作转交给程序员即可。你设计的一切都必须可以成功地构建、测试，并且要精益求精。这就是为什么在现代游戏开发中，测试者从项目一开始就被引入，而不是像以前一样在结束时才匆匆加入。作为设计师，在游戏的开发过程中你不会有太多的机会来进行管控，除非碰巧你还是该游戏项目的领导者。在这个阶段，你将与团队的其他成员密切合作，并做一些可以帮助他人的必要工作：如细化游戏机制、测试用户界面、计划关卡和许多其他任务等。在概念阶段你或许不会制定在游戏中可能出现的所有角色或单位的所有详细信息，因此你将在开发过程中继续这个工作。如果游戏使用了大量口语单词的音频，你可能正在写这种素材和记录这些过程。你还将回答来自其他开发人员（特别是程序员）的关于应该如何工作的问题。总而言之，你将会测试游戏——即使只完成了一小部分——确保它做了你想要它做的事情，并且目标受众的成员按照你的预期回应了它。游戏开发/Scrum管理过程在过去几年里，许多大大小小的游戏开发团队都开始实行一个名为Scrum的项目管理过程（Scrum不是一个首字母缩略词，这个术语是从橄榄球运动中借鉴过来的）。Scrum过程可以帮助团队组织和跟踪完成某些工作的进展，通常用于新产品开发上。在Scrum过程中，团队通过简短的迭代（称为“冲刺”，sprint）创建和测试产品的更新版本。每个冲刺持续一到四周，团队不断进行检查和调整，以有效地实现他们临时和最终的目标。这使他们能够在早期便能识别和解决问题。此外，团队每天都举行一次非常简短的会议，所有问题必须在这里提出——没有层级阻碍。当一个团队致力于Scrum方法时，管理者对任何时候发生什么都有清晰的了解，这有助于确保工作按时完成。本书是关于游戏设计，而不是游戏开发的，因此本书不会更详细地讨论项目管理或Scrum。此外，Scrum更多地用于实际构建产品，特别是软件，而不是设计。不过，如果读者渴望成为一个商业游戏开发商，那么你一定要了解它。更多有用信息请阅读Ken Schwaber（Schwaber，2004）的《Scrum敏捷项目管理》一书。你将在互联网上找到更多Scrum资源。有关游戏开发管理的详细信息，请参阅《游戏架构和设计》（Rollings和Morris，2003）。
