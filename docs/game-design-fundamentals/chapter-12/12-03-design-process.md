# 12.3 设计过程

> 来源：原书第 12 章 OCR 整理。扫描/OCR 文本已做基础清洗，仍建议对照原书复核术语和图注。

## 原书内容整理

设计过程你将回忆起在第2章中我们把游戏设计过程分为三个阶段：概念设计阶段、详细设计阶段和调整阶段。设计用户界面发生在详细设计阶段。没有理由更早地设计它，如果你在概念设计阶段结束之前设计了它，那么整个设计可能会发生很大的变化并且早期的UI设计工作就白费了。

在这一部分，我们给出UI设计过程的步骤。记住你在设计游戏的UI组件用到的很多定义都可以在本章的后面找到。

提在大型开发团队中，首席设计师和用户界面设计师通常由不同的人担任。为简单起见，本章假设读者将同时执行这两项工作。

### 12.3.1 首先定义游戏的主要游戏可玩性模式

首先定义游戏可玩性模式游戏可玩性模式由摄像机视角、交互模型和可用的游戏可玩性（挑战和动作）组成。这个术语通常是在概念设计阶段定义游戏可玩性模式将会给游戏带来什么，在详细设计阶段，开始详细地设计游戏可玩性模式。

在任何情况下，第一个工作都应该是设计主要游戏可玩性模式，玩家在这种模式下花费了大部分时间。参考12.5节和12.6节来了解交互模型和视角的细节。一旦你选择了（或者被给定）主要游戏可玩性模式的视角、交互模型和游戏可玩性，那么就可以开始创造在这种模式下的用户界面的细节了。

当已经设计了主要游戏可玩性模式后，把自光转移到其他你认为游戏可能需要的可玩性模式上。使用第2章中描述的流程板来计划游戏的结构。处理游戏可玩性活动时，不要忘记与故事相关的活动。设计发布叙事内容和涉及对话的模式，如果你的游戏支持的话。

还必须保证它包含一个中断叙事（如果是实时游戏），并返回到游戏可玩性以及中断菜单的方法，以防玩家突然接听电话。

游戏可玩性模式并不是都使用完全不同的用户界面，而是共享一部分UI特征，所以最好在开始设计UI工作之前定义所有的模式。如果你的游戏提供了少量的游戏可玩性模式（例如五个或者更少），那么一旦确定了每种模式的目的以及玩家会在每种模式做什么，你就可以开始设计用户界面了。然而，如果游戏提供了很多数量的模式，那么你就应该等待，直到你已经计划好了游戏的结构以及理解了游戏如何从一个模式转移到另一个。

一旦有了一个游戏可玩性模式列表，你就可以开始思考每个模式将需要什么样的视觉元素和控制。使用图纸或者像MicrosoftVisio这样的表格工具，制作顺序流程图中的菜单、对话框和打算在每个模式中使用的其他用户界面元素，也要记录下输入设备在每一种模式下的行为。

你通常需要为游戏提供的每一种游戏可玩性模式定义一个不同的用户界面。当游戏可玩性模式只在它们提供的挑战上不同的时候，它们可以共享单一的UI。如果你希望允许玩家控制从一种模式到另一种的改变，那么用户界面也应该提供完成这些模式改变的命令。

设计一个用户界面的步骤包括：为每一种模式设计一个屏幕布局，选择告诉玩家需要知道的视觉元素，并且定义玩家希望游戏做的输入。我们将依次讲述这些话题。在这个讨论的剩余部分，我们将假设你正在为最重要的模式——主要游戏可玩性模式——设计用户界面，虽然这同样适用于任何其他模式。

开发实例：构建一个原型UI有经验的设计师在设计实际的用户界面之前都构建并测试一个UI原型。当你有了设计好的模式的UI元素的名字和功能后，就可以用正在运行的美术作品和声音来构建一个原型，那样你就可以看到设计是怎样运行的。不要假设你会在最终产品上使用它，而在美术或者声音上花费过多的时间。如果计划改变，那么你就有可能抛弃它。

很多优秀的工具都在使用最少编程工作的前提下允许制作包括图形和声音的界面原型。

你可以在MicrosoftPowerPoint中使用超链接使各个幻灯片之间能够切换来制作非常简单的原型。AdobeFlash提供了更强大的功能，如果你会一点程序设计，那么其他的像BlitzBasic（www.blitzbasic.com）等游戏制作工具也可以让你构建界面原型。对于手机游戏，你可以在索引卡上制作纸上模型，并且玩它们看看感觉如何。

原型不是一个可玩的游戏，只是显示菜单和屏幕按钮并对输入设备的信号做出反应。

它应该在没有游戏软件支持的情况下尽可能准确地做出反应。如果一个菜单项引起转换到一个新的游戏可玩性模式，那么就要把这种模式构建到其中。如果一个控制器按钮可以发射一道激光，那么构建的原型至少应该发出“磁”的声音来确认按下了按钮。

设计不是一次完成的。每设计一个游戏可玩性模式时，都应该尽早构建并观察是否达到预期；不要一次构建所有模式，而要逐步构建、测试、修改，然后再加入复杂性。

### 12.3.2 选择一个屏幕布局

如果你清楚地理解了玩家在主要（或者任意的）可玩性模式中将做什么，以及你已经选择了一种交互模型和视角，那么接着你就必须选择总体屏幕布局和它应包括的视觉元素。

所有屏幕上的UI特征都应该放置在游戏世界的主视野上以及它的周围。主视野将是屏占据整个屏幕，或者是否一部分由于覆盖物而变得模糊。参考12.7.1节，寻找有关选项的更多信息。

你应该在主视野占据的屏幕空间和反馈元素和屏幕控制占据的屏幕空间之间找到一个平衡点。幸运的是，在个人计算机和控制台游戏上这根本就不算是一个问题，因为它们都使用高分辨率的屏幕。对掌上设备来说，这还是一个严重的挑战，而对手机来说，这就是一个非常严重的挑战了，因为手机还没有一个标准的屏幕大小和形状。

### 12.3.3 告诉玩家需要知道的东西

除了游戏世界中当前的景象，玩家还需要看到或者知道什么？他需要一直知道什么是关键的资源，什么是让他得到这些信息的最好方式？从核心机制中选择你希望展示的数据，把12.7.2节中的反馈元素列表作为指导，选择最适合显示数据的反馈元素。也问一下你自己：玩家可能需要什么警告，然后才能决定如何提供视觉和听觉的提示。使用在12.2.3节中给出的一般列表，但是要记住你提供的可玩性模式可能规定了一个稍微不同的列表，你的游戏可能会包含以前从未使用过的独特元素。举个例子，如果一个游戏是关于服装设计的，那么它里面应该包含一种名为“独创性”的特殊属性，你可以使用不同的T恤符号来表示该属性的不同等级，从平淡的白色T恤（独创性很低）到打着领带的夸张的T恤（独创性很高）。

一且你已经定义好了重要的信息，那么就可以开始考虑那些可选的信息了。玩家可能会要求什么额外的数据？一个地图？一个对游戏世界不同角度的观察？思考什么反馈元素可以帮助他获得这些东西以及怎样组织对这些特征的访问。

在这个过程中，要时刻把优秀用户界面设计的一般原理记在脑海中，测试你的游戏是否违背了12.2.2节中列出的一般原理。

### 12.3.4 让玩家做想做的事情

现在你可以开始设计合适的控制机制来发起玩家可以采用的影响游戏的每一个动作（不管是在游戏世界内还是游戏世界外，例如保存游戏）。开始的时候可以参考12.2.4节提供的列表。

射，有时则更糟。例如，如果玩家想要游戏人物在游戏中跳跃，则Kinect可以检测到玩家在自己的客厅中的身体跳跃。而另一方面，如果是转动的话，则不能很好地工作；如果玩家在客厅里转身，那玩家将不再面向屏幕。同样，需学习其他游戏，看看他们如何处理这些问题。

玩家将会采用什么样的关键动作来克服挑战？参考相关书籍中关于每种游戏类别的特殊UI关注。她可能需要什么跟挑战无关的动作：移动视角、参与故事，或者和其他的在线玩家交谈？创建这些动作的视觉和听觉反馈来让玩家知道这些动作是否成功。

基于选择的交互模型，你需要把输入设备和玩家在游戏中的动作映射起来（见12.5节）。游戏变化非常大，我们不能确切地告诉你怎样才能达到好的映射。研究相同类别其他的游戏，看看它们是怎样使用屏幕上的按钮和菜单或者物理按钮、控制杆和控制设备上其他配件的。对于玩家动作来说，使用后者可以让玩家感到她能直接产生游戏中的动作，不是经过菜单调整的。任何可能的时候，都要借鉴可靠的技术来保持她对所有的事物都是尽可能的熟悉。

因此设计一种游戏可玩性模式，每次当你移动到一个新的游戏可玩性模式时，要注意那些跟其他模式相同的动作并保持控制机制一致。

### 12.3.5 Shell 菜单

“shell菜单”（shell menu）允许玩家开始和配置以及在游戏开始之前或者结束之后管理游戏的操作。shell界面的屏幕和菜单应该允许玩家配置视频和音频选项以及游戏的控制（详见本章12.11节），通过网络加入多玩家游戏，保存和载入游戏，以及关闭游戏软件。

玩家不应该在shell菜单上花费过多的时间。提供一种方法，使玩家通过点击一两个按钮就可以立即进入游戏。

有惊人数目的游戏使用了糟糕和丑陋的shell菜单，因为设计者认为可以直到最后一分钟再设计这些屏幕。记住，shell界面是玩家在打开游戏软件之后首先看到的界面，你应该不会希望在玩家还没有开始玩游戏时就给他留下一个不好的印象吧！
