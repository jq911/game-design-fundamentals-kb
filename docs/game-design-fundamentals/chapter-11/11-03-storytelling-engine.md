# 11.3 故事讲述引擎

> 来源：私人资料库 OCR 整理，摘自《游戏设计基础（原书第 3 版）》第 11 章。PDF 为扫描版，文字已做轻度校正，仍建议以后逐段人工复核。

## 原书内容整理

为了设计一个包含故事的游戏，你必须把游戏可玩性——克服游戏挑战所采用的动作——与故事的叙事事件交织到一起。叙事事件必须按照以下方式散布在游戏可玩性事件之中，即所有的事件都应该感觉彼此是相关的，而且都应该是可以娱乐玩家的故事片段的一部分。如果游戏可玩性涉及和叙事相同的主题——为了呈现出一个连贯与和谐的整体，它应该这样——那么整个体验、游戏和叙事组合在一起，会感觉像一个连续的故事。

故事讲述引擎完成交织的工作。我们在第2章中简要地介绍了故事讲述引擎，它是电子游戏的第三主要组件，其他两个是核心机制和用户界面。和其他两个组件不同，故事讲述引擎是可选的，如果游戏没有讲述故事，那么就没有故事讲述引擎。

就像核心机制产生游戏可玩性一样，故事讲述引擎负责把叙事事件交织到游戏中。核心机制管理玩家通过游戏挑战的进度，故事讲述引擎管理玩家通过游戏故事的进度。故事讲述引擎和核心机制必须一起工作来创造一个单一的无缝的体验。

你可能会注意到它和第2章中的图2-1非常像，图2-1显示了核心机制是怎样产生和管理游戏可玩性的。就像我们在前面11.2.1小节中讲到的那样，-个交互式故事包含三种事件类型：玩家事件、故事内事件和叙事事件。核心机制管理玩家事件和故事内事件，故事讲述引擎管理叙事事件。然而，故事讲述引擎所做的不仅仅是播放电影或者场景插叙，它也跟踪故事的进度并决定下面应该出现哪一部分情节。

注意图11-1中标有“触发器”的双箭头把故事讲述引擎和核心机制连接起来了。有时，核心机制会在适当的时候向故事讲述引擎发送一个消息说明玩家完成了一关，故事讲述引擎现在应该显示关卡间的叙事事件。同样，当一个叙事事件结束之后（或者当玩家中断了一个叙事时间时），故事讲述引擎也可以向核心机制回送一个触发信号，告诉核心机制返回游戏。

这是最简单的，也是在小游戏中最为常见的故事讲述引擎。《愤怒的小鸟》中由系统展示出关卡之间的场景插叙便是如此的。

而在更加复杂的大型游戏里，在玩游戏期间故事讲述引擎也没有空闲。当玩家前进时，核心机制持续地触发故事讲述引擎——那样，故事讲述引擎就可以一直知道当前进行的内容。例如，如果玩家做出了一个重要决定，这个决定会影响后面的故事，那么核心机制就会把这个决定通知给故事讲述引擎。

同样，在游戏过程中，故事讲述引擎也可以决定故事达到了一个关键点，并且触发核心机制来改变游戏内部经济。假设故事说：“当化身到达桥上的时候，他会在一个场景插叙中遭到拦路抢劫，并且抢走他所有的财产。”由于跟踪了玩家在游戏世界中的进度，核心机制会向故事讲述引擎发送一条消息“化身已经到达桥上”。故事讲述引擎检测到这是一个关键点，然后暂停游戏，显示抢劫的场景插叙。然后它向核心机制回复一条消息“把化身的财产转移到拦路盗贼身上并返回游戏。

正常情况下，关卡设计师做那些在游戏中实际实现这些事件的工作。在关卡设计师的关卡构建工具中会有检测玩家位置的技术和触发场景插叙以及化身财产转移的技术。这时，开发公司不能像许可一个图形引擎或者物理引擎一样，对中间件公司许可一个故事讲述引擎，但是以后这可能会改变。如果你利用这两个独立组件（核心机制和故事讲述引擎）之间发送触发信息的方式来考虑这些事件，那么在概念设计阶段，它仍然可以帮助你设计故事和它跟游戏可玩性的交互。

正如你能看到的，故事讲述引擎在把游戏可玩性和叙事交织在一起创造一个完整的体验方面发挥了关键的作用。在本章的其他部分，我们会频繁地引用故事讲述引擎。
